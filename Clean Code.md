# Clean Code: Каталог рефакторингов и TODO Roadmap

Этот документ определяет направления развития проекта **`reforge`** в соответствии с принципами **Clean Code** (Роберт Мартин), каталогом **Refactoring** (Мартин Фаулер) и идиомами современного **OCaml**.

Документ состоит из двух частей:
1. **Каталог автоматизированных рефакторингов для CLI `reforge`** — функциональность, которую инструмент предоставляет инженеру для наведения порядка в OCaml-кодовых базах.
2. **Внутренний Clean Code долг самого проекта `reforge`** — задачи по поддержанию чистоты архитектуры, модульности и читаемости текущего репозитория.

---

## Часть 1. Каталог рефакторингов для реализации в `reforge` (CLI Roadmap)

### 1. Понятные и точные имена (Meaningful Names)

> *"Имя переменной, функции или класса должно отвечать на главные вопросы: почему это существует, что делает и как используется." — Clean Code*

- [x] **`plan rename-fn <FILE> <OLD> <NEW>`** — переименование функции на уровне репозитория (определение, `.mli`, внешние вызовы). *(Реализовано)*
- [x] **`plan rename-arg <FILE> <FN> <OLD> <NEW>`** — переименование аргумента функции (позиционного, именованного `~lbl` или опционального `?opt`). *(Реализовано)*
- [x] **`plan rename-type <FILE> <OLD_TYPE> <NEW_TYPE>`** — переименование типа во всех объявлениях (`type ... = ...`), аннотациях типов (`(x : old_type)`) и интерфейсах `.mli`; учёт скоупов при квалифицированном доступе `Module.old_type`. *(Реализовано)*
- [ ] **`plan rename-module <SRC_MODULE> <NEW_MODULE>`**
  - Переименование модуля внутри файла (`module Old = ...`) или переименование файла с обновлением всех квалификаторов вида `Old.foo` $\to$ `New.foo` и `open Old` $\to$ `open New`.
- [ ] **`plan rename-field <FILE> <TYPE> <OLD_FIELD> <NEW_FIELD>`**
  - Переименование поля записи (record field) в типе, литералах создания `{ old_field = 1 }` и pattern-matching `{ old_field }`.
- [ ] **`plan rename-constructor <FILE> <TYPE> <OLD_CTOR> <NEW_CTOR>`**
  - Переименование конструктора вариантного типа (`| Old_tag of int` $\to$ `| New_tag of int`) во всех сопоставлениях с образцом и местах создания.

---

### 2. Функции: компактность и единая ответственность (Small & Single-Purpose Functions)

> *"Первое правило: функции должны быть компактными. Второе правило: функции должны быть ещё компактнее. Функция должна делать только одну вещь и делать её хорошо." — Clean Code*

- [x] **`plan move-fn <SRC> <DST> <FN>`** — перенос функции в специализированный модуль для разделения зон ответственности. *(Реализовано)*
- [ ] **`plan extract-fn <FILE> <RANGE> <NEW_FN_NAME>`**
  - Выделение фрагмента AST/выражения в локальную или верхнеуровневую функцию.
  - Автоматический расчет свободных переменных, необходимых в качестве аргументов.
  - Определение возвращаемого типа и подстановка вызова `new_fn_name arg1 arg2 ...` на место фрагмента.
- [ ] **`plan inline-fn <FILE> <FN>`**
  - Замена вызовов короткой или тривиальной функции её телом (при устранении лишней косвенности или временных алиасов).
  - Проверка на отсутствие конфликтов имен переменных в месте инлайнинга.
- [ ] **`plan decompose-match <FILE> <FN>`**
  - Автоматическое вынесение ветвей сложного `match` в отдельные чистые функции-обработчики (pattern branch $\to$ dedicated function).
  - Помогает уменьшить цикломатическую сложность больших функций-диспетчеров.

---

### 3. Аргументы функций: чистота сигнатур (Clean Signatures)

> *"Идеальное число аргументов функции равно нулю (niladic). Затем идет один (monadic), два (dyadic). Трех аргументов (triadic) следует по возможности избегать." — Clean Code*

- [x] **`plan remove-arg <FILE> <FN> <ARG>`** — безопасное удаление неиспользуемого аргумента с валидацией отсутствия обращений в теле. *(Реализовано)*
- [x] **`plan label-arg <FILE> <FN> <ARG> <LABEL>`** — преобразование позиционного аргумента в именованный (`~label`) с обновлением сигнатур `.mli` и всех мест вызовов (включая punning). *(Реализовано)*
- [x] **`plan unlabel-arg <FILE> <FN> <LABEL>`** — обратная операция к `label-arg`: перевод именованного аргумента в позиционный с проверкой, что порядок аргументов на всех вызовах не изменит связывание (отклоняет `?opt`-аргументы). *(Реализовано)*
- [ ] **`plan introduce-param-object <FILE> <FN> --args <A,B,C> --record <TYPE_NAME>`**
  - Объединение группы тесно связанных аргументов (контекст, конфигурация, координаты) в единый тип `record`.
  - Генерация объявления типа записи, упаковка аргументов в вызывающем коде `{ a; b; c }` и распаковка/использование записи в целевой функции.
- [ ] **`plan reorder-args <FILE> <FN> <NEW_ORDER>`**
  - Изменение порядка аргументов функции.
  - Критично для OCaml и конвейеров пайплайна (`|>`): перемещение главного операнда данных на последнюю позицию для удобной композиции.

---

### 4. Борьба с примитивной одержимостью и явные типы (Types & Value Objects)

> *"Не полагайтесь на сырые строки и инты там, где понятие домена требует строгости." — Domain-Driven Design & Clean Code*

- [ ] **`plan wrap-primitive <FILE> <TYPE_NAME> = <PRIMITIVE>`**
  - Введение абстрактного типа или типа-обёртки (Value Object) вместо примитива (например, `type user_id = private string` или `type path = Path of string`).
  - Замена прямых использований примитива в сигнатурах модуля.
- [ ] **`plan replace-exception-with-result <FILE> <FN>`**
  - Замена функции, выбрасывающей `raise ...`, на возвращающую `('a, error) result`.
  - Обновление интерфейса `.mli` и вставка конструкторов `Ok (...)` / `Error (...)`.

---

### 5. Мертвый код и устранение дублирования (Dead Code & Hygiene)

> *"Мертвый код — это рассадник бактерий. Удаляйте код, который больше не используется." — Clean Code*

- [ ] **`plan remove-unused-fn <FILE> <FN>`**
  - Анализ графа зависимостей и удаление функции, к которой нет внешних обращений и которая не экспортирована наружу.
- [x] **`plan remove-unused-opens <FILE>`** — поиск операторов `open Module`, ни один идентификатор из которых не используется в файле без квалификации, и их безопасное удаление. Opens с неразрешимыми экспортами (внешние модули, re-export через `include`) сохраняются с предупреждением. *(Реализовано)*
- [ ] **`plan qualify-open <FILE> <MODULE>`**
  - Замена глобального `open Big_module` на локальные `let open Big_module in ...` или явные квалификаторы `Big_module.func`, предотвращая загрязнение пространства имен (Namespace Pollution).
- [x] **`plan extract-constant <FILE> <LITERAL> <CONST_NAME>`** — поиск повторяющихся строковых или числовых литералов (Magic Numbers / Magic Strings) и вынос их в именованное значение `let const_name = ...`. *(Реализовано)*

---

### 6. Модули, интерфейсы и границы (Encapsulation & Boundaries)

> *"Хорошо спроектированный модуль скрывает детали реализации и предоставляет чистый, минимальный интерфейс." — Clean Code*

- [ ] **`plan extract-mli <FILE>`**
  - Автоматическая генерация минимального интерфейса `.mli` на основе фактических публичных вызовов из других модулей репозитория (приватные вспомогательные функции остаются инкапсулированными внутри `.ml`).
- [ ] **`plan sync-mli <FILE>`**
  - Двусторонняя синхронизация: удаление из `.mli` деклараций удаленных функций и добавление сигнатур для новых экспортируемых функций.
- [ ] **`plan split-module <FILE> --modules <Sub1,Sub2>`**
  - Разделение разросшегося файла ("God Module" / "Large Class") на несколько подмодулей или отдельных файлов с сохранением общей точки входа.

## Часть 2. Clean Code TODO для самого проекта `reforge` (Codebase Health)

Текущее состояние архитектуры: строгое разделение DDD и гексагональная архитектура (Ports & Adapters) уже заложены. Для поддержания идеальной чистоты кодовой базы определены следующие задачи:

### 1. Декомпозиция CLI и роутера (`lib/cli/command_router.ml`)
- [ ] **Вынести команды из монолитного `command_router.ml`**:
  - `command_router.ml` сейчас содержит обработчики для всех подкоманд (`scan`, `tree`, `inspect`, `deps`, `cycles`, `report`, `plan_*`, `apply`, `preview`, `validate`, `undo`).
  - **Цель**: создать подпапку `lib/cli/commands/`:
    - `cmd_inspect.ml`
    - `cmd_graph.ml` (`deps`, `cycles`, `report`)
    - `cmd_plan.ml` (`plan move`, `plan rename-fn`, `plan move-fn`, `plan rename-arg`, `plan remove-arg`)
    - `cmd_lifecycle.ml` (`apply`, `preview`, `diff`, `validate`, `undo`, `status`)
  - В главном роутере оставить только регистрацию Cmdliner-термов.

### 2. Рефакторинг AST-анализатора (`lib/infrastructure/ocaml_analyzer.ml`)
- [ ] **Разделение визиторов AST (Single Responsibility)**:
  - Сейчас один и тот же файл отвечает за извлечение модулей, ссылок, определений функций, параметров, типов и вызовов.
  - **Цель**: разбить на специализированные визиторы:
    - `analyzer_module_defs.ml`
    - `analyzer_references.ml`
    - `analyzer_function_defs.ml`
    - `analyzer_call_sites.ml`
- [ ] **Отказ от ручной строковой манипуляции смещениями**:
  - Постепенно перевести форматирование и замену аргументов/вызовов с символьных срезов на AST-rewriting (Ppxlib / Pprintast) там, где это сохраняет исходные комментарии и форматирование кода.

### 3. Обработка ошибок и предметные сообщения (`lib/domain/refactoring.ml`)
- [ ] **Структурированный тип для ошибок валидации**:
  - Тип `plan_error` растет с каждым новым рефакторингом (`Fn_not_found`, `Arg_collision`, `Arg_in_use`, ...).
  - Разделить ошибки на категории:
    - `precondition_error` (исходный файл не найден, хеш устарел, файл занят)
    - `symbol_error` (функция/аргумент не найдены, дубликат имени)
    - `safety_violation` (аргумент используется в теле, цикл зависимостей)
  - Добавить контекстную подсказку к каждой ошибке (`suggestion : string option`), например: *"Подсказка: возможно, вы имели в виду `~format` вместо `~fmt`?"*.

### 4. Тестирование и качество (Test Suite & Verification)
- [ ] **Property-Based Testing для `Path` и `Change_plan`**:
  - Подключить `qcheck` / `crowbar` для генерации случайных путей и последовательностей правок файла для гарантии, что пересекающиеся правки всегда либо корректно сшиваются, либо детерминированно отклоняются.
- [ ] **Фьючерсные тесты для OCaml 5.x синтаксиса**:
  - Добавить тесты на глубокие паттерны в аргументах функций: деструктуризация кортежей `let f (a, b) = ...`, деструктуризация записей `let f { id; name } = ...` и локальные типы `let f (type a) (x : a) = ...`.
